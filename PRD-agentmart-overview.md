## 1. Overview

AgentMart is a merchant-side e-commerce platform built for AI shopping agents as first-class customers. Unlike a binary "verified/unverified" agent gate, purchasing authority is governed by a **live, multi-component trust score** rather than a single opaque flag. Every integration point — identity, checkout, card issuance, settlement — talks over real HTTP and real StraitsX rails. Nothing in the demo path is simulated.

Three pieces, run separately:

```
backend/      FastAPI + SQLite — the merchant API (products, identify, checkout,
              authorise, receipt, audit, merchant dashboard endpoints)
demo_agent/   Claude-powered shopping agent — a CLI that calls the backend over
              HTTP, same as any other agent would
frontend/     Vue 3 — agent demo view + merchant dashboard, polling the backend live
```

## 2. Core Purchase Flow

Matches the deck's own six-step agent payment lifecycle:

```
/identify → /checkout → /authorise → /receipt
```

- Session tokens are signed JWTs, now **Ed25519 (EdDSA)**, not a shared HS256 secret — AgentMart holds one issuer keypair (`backend/issuer_private_key.pem` / `issuer_public_key.pem`, generated by `scripts/generate_issuer_keypair.py`); verification only needs the public half. Still "signed JWTs, not a full PKI" per the non-goal in §8 — asymmetric keys, not a certificate authority.
- **Identity and mandate are frozen into the token at issuance** — they cannot be silently upgraded mid-session.
- Everything transaction-specific (price validity, behavior, payment outcome) is **recomputed live** at each stage rather than trusted from the token.
- **Revocation is instant and live**, not certificate-expiry based: each agent carries a `key_active` flag, checked on every request (`app/deps.py`). A merchant can flip it via `POST /merchant/agents/{id}/revoke` (and reverse it via `/reinstate`) — the agent's current session token stays *signature*-valid but is rejected on its very next call. Both actions are logged to the activity feed.

## 3. StraitsX Integration (real, not mocked)

`straitsx_client.py` connects to StraitsX's actual MCP server:

- Calls `get_card_sandbox` / `get_card_prod` over SSE to discover the card API URL.
- Runs the real **x402 + EIP-3009** flow: 402 challenge → sign `TransferWithAuthorization` → retry with `PAYMENT-SIGNATURE` header → card issued.
- **Safety check:** client refuses to sign if the challenge's asset/chainId doesn't match the active profile.

**Bugs found and fixed along the way:**
- Cardholder names needed sanitizing — StraitsX rejects hyphens.
- MCP-discovery step needed to be wired in explicitly (not automatic).

## 4. Trust Score Engine (v2)

Five components, blended differently at different pipeline stages — never a single frozen number:

| Component | Computed at | Notes |
|---|---|---|
| `identity_score` | `/identify` | Frozen — who the agent is. Shape-checked credential (looks JWT-like) + issuer reputation. Now double-gated: `IDENTITY_GATE` (50) hard-blocks `/checkout` on a weak identity signal, mirroring the commercial-validity gate — otherwise identity is only 30% of the blend and a credential that fails the shape check can still clear the highest price tier on a disciplined-looking mandate alone |
| `mandate_scope_score` | `/identify` | Frozen — what it's authorized to do (spend cap, merchant whitelist size, expiry window) |
| `behavior_score` | Live | Blends request velocity with `reputation_score`, a **Wilson score interval** lower bound over the agent's own resolved order history (same statistic Reddit uses to rank comments). Checkout-blocked and infra-failed orders are excluded from trial counts; a merchant-override-assisted completion counts as a trial but **not** a clean success. Zero order history → reputation is skipped, not defaulted to "average" |
| `commercial_validity_score` | `/checkout` | Agent may assert `expected_price_sgd`; a >5% mismatch vs. catalog **hard-blocks regardless of overall score** |
| `payment_authority_score` | `/authorise` | 100 on real settlement; **excluded (not penalized)** on a StraitsX-side infra failure |

Every checkout/authorise decision now also carries a structured `denial_reason` (`identity_verification_failure` / `commercial_validity_failure` / `insufficient_trust` / `straitsx_error`) alongside the free-text `reason`, so the dashboard can aggregate and chart *why* orders are blocked without parsing prose.

Full breakdown is visible on every API response, in the per-agent dashboard panel, and in a per-order timeline — the score is never opaque.

## 5. Merchant Dashboard

- **Live activity feed**, now cursor-paginated (`GET /activity/feed?since_id=`/`before_id=`) instead of a fixed top-50 poll: the dashboard fetches only what's new since its last-seen event on each 2s poll (`since_id`) and can page back into older history on scroll (`before_id`), with a `has_more` flag so the client knows whether it's caught up or there's more to load. `AuditEvent.id`, not timestamp, is the cursor — an autoincrementing PK sidesteps millisecond tie-breaks under concurrent writes.
- Rule builder: category caps, price thresholds, blocked categories (read live by `/checkout`)
- Order table with override control for blocked orders, and a revoke/reinstate control per agent
- Per-agent trust breakdown (4 bars, including reputation) plus a **trust trajectory chart** showing how an agent's score has moved over time, not just its current value
- Click-to-expand per-order timeline showing the score move stage-by-stage

## 7. Deployment

- `vercel.json` at repo root builds the frontend from `frontend/` (`npm install` / `npm run build` → `frontend/dist`) for Vercel hosting.
- `frontend/.env.example` documents `VITE_BACKEND_URL` (falls back to `http://127.0.0.1:8000` for local dev; set as a Vercel project env var to the deployed backend's public URL).
- `backend/.env.example` documents adding the Vercel origin to `CORS_ORIGINS` once the frontend is live.
- Backend itself is not yet deployed anywhere (Vercel config only covers the frontend) — a host for the FastAPI service is still needed for a fully hosted demo.

## 8. Verified So Far ✅

- Real sandbox end-to-end settlement (repeatedly)
- Commercial-validity hard-block on a tampered price (screenshotted, dashboard-visible)
- Insufficient-trust rejection on a genuinely bad agent, at real quantity = 1
- Reputation math validated against known Wilson-interval behavior + isolated integration tests (blocked orders don't count; override-assisted completions count as a trial but not a success)
- Live credential revocation: a revoked agent's still-unexpired token is rejected on its next request
- Activity feed pagination: incremental `since_id` polling and `before_id` backfill both tested against the dashboard's infinite-scroll feed

## 9. Known, Named Gaps

State these confidently in the demo — they're scoped, not hidden:

- **Prompt injection:** explicitly "on you," not handled — matches the deck's own framing of this as unsolved.
- **Identity verification** is shape-checked (JWT-like structure) plus issuer-allowlist reputation, not real PKI signature verification against an external issuer — explicit non-goal for this build. (AgentMart's *own* issuer keys are now real Ed25519 — this gap is specifically about verifying the *agent's* credential, not AgentMart's signing.)
- **StraitsX sandbox flakiness:** the sandbox has been flaky multiple times (bugs on their side, not ours) — worth having a recorded backup demo rather than relying on a live-only run.
- **No real mainnet settlement proven yet** — production path is wired and funded but unexercised.
- **Backend has no hosted deployment yet** — Vercel config covers the frontend only.
