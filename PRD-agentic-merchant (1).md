## 1. One-liner
A mock e-commerce storefront (think eBay) rebuilt from the ground up with an
API layer designed for AI agents as first-class customers — not a checkout
form with an agent bolted on top.

## 2. Problem
Existing e-commerce sites are built for humans: visual layouts, forms,
redirects. Agents stumble through them. Nobody has designed the merchant
side properly for agent traffic yet — that's the gap this track exists to
fill.

## 3. Goals (weekend scope)
- [ ] A working product catalogue an agent can query via clean, machine-readable API (no scraping)
- [ ] Agent identity verification before any purchase is allowed
- [ ] End-to-end checkout flow that settles a real (sandbox) transaction via
      StraitsX's one-time card MCP, in $XSGD on Avalanche C-Chain
- [ ] A signed, tamper-evident receipt/audit trail per Milestone 6 ("Prove")
- [ ] **USP: Trust scoring** — agents aren't all trusted equally; spend
      limits and allowed actions scale with a computed trust score
- [ ] A live demo view showing an agent shopping step-by-step (discover →
      identify → checkout → authorise → prove)

## 4. Non-goals (explicitly out of scope for the weekend)
- Building our own payment rail (we consume StraitsX's MCP, not reinvent it)
- A polished human-facing shopping UI (this is a merchant-for-agents product,
  not a B2C site — the "storefront" is API-first)
- Full PKI / production-grade cryptography — use signed JWTs or similar,
  not a custom cert authority
- Multi-merchant support — one mock storefront is enough

## 5. Users
| User | Description |
|---|---|
| **Shopping agent** | An LLM-driven agent (our demo agent, built on Claude) acting on behalf of a human buyer with a mandate (spend cap, merchant whitelist, expiry) |
| **Merchant (us)** | The API + catalogue + trust engine, standing in for "eBay" |
| **Human owner** | The person who set the agent's mandate — mostly implicit for demo purposes, surfaces in escalation flows if built |

## 6. Core user flow (the demo script)
1. Human types a prompt into our demo agent: *"buy me a birthday gift under $50"*
2. Agent calls `GET /products` to browse the mock catalogue
3. Agent calls `POST /identify` presenting a signed credential — merchant
   verifies it's a legitimate, mandate-bound agent
4. Merchant computes/looks up a **trust score** for this agent based on
   mandate scope + identity signal
5. Agent calls `POST /checkout` with the chosen SKU — merchant checks trust
   score against required threshold for this purchase (price, category)
6. Agent calls `POST /authorise` with a StraitsX one-time card credential —
   merchant validates it covers the amount, executes the charge via StraitsX
   MCP, settles in XSGD
7. Merchant returns a signed receipt (`GET /receipt/{order_id}`) — logged to
   an append-only audit trail
8. Demo dashboard renders all 6 steps live as they happen

## 7. API surface (draft)

| Endpoint | Method | Purpose |
|---|---|---|
| `/products` | GET | Machine-readable catalogue: SKU, name, price, description, category |
| `/products/{sku}` | GET | Single product detail |
| `/identify` | POST | Agent presents signed credential; merchant verifies + returns a session token + trust score |
| `/checkout` | POST | Agent requests to buy a SKU; merchant checks trust score vs. purchase risk, returns checkout intent |
| `/authorise` | POST | Agent submits StraitsX one-time card credential; merchant validates and triggers charge via StraitsX MCP |
| `/receipt/{order_id}` | GET | Signed proof of purchase, tamper-evident |
| `/audit/{order_id}` | GET | Full step-by-step log for that order (supports the "Prove" milestone) |

### Trust score inputs (rough draft, refine with team)
- Mandate scope tightness (narrow whitelist/cap = higher trust)
- Signature/identity verification result (pass/fail, plus issuer reputation if available)
- Behavioural signal (e.g. request velocity, repeat identify attempts — flag anomalies)
- Purchase risk (price tier, category sensitivity) → determines required trust threshold

## 8. Merchant experience (dashboard + rule builder)

The problem statement explicitly asks for "merchant experiences," not just
APIs and protocols. Everything in Sections 6-7 is the *agent's* experience
calling our system — this section is the *human merchant's* experience
running it. Without this, the demo only answers two-thirds of the track.

Both pieces below reuse data already generated by the core flow (trust
scores, checkout decisions, transaction logs) — no new backend logic
required, just a merchant-facing view and a ruleset the checkout logic
reads from instead of hardcoded thresholds.

### 8.1 Merchant dashboard (must-have)
A screen in the demo frontend, separate from the "watch the agent shop"
view, showing the store owner's side of things:

- **Live activity feed** — each agent interaction as it happens, e.g.
  *"Agent #4521 requested $80 headphones — trust score 62 — capped at $50 —
  blocked"*. Pulls straight from `/audit` data, just rendered from the
  merchant's point of view instead of the agent's.
- **Trust score breakdown per agent** — show the inputs feeding a given
  score (mandate scope, identity verification result, behavioural signal)
  so it's not a black box, this also doubles as a nice visual for judges
  during Q&A.
- **Manual override control** — a button to approve a blocked transaction
  anyway. Doesn't need real logic beyond flipping the order status, but it
  makes the point that the merchant stays in control, not just the trust
  engine.

### 8.2 Rule builder (stretch, build after 8.1 and core flow both work)
A simple settings panel where the merchant sets policy, and `/checkout`
actually reads from these merchant-set rules instead of hardcoded trust
thresholds:

- **Category spend caps** — e.g. "electronics: max $50 for trust score
  under 70"
- **Price-tier trust thresholds** — e.g. "purchases over $100 require trust
  score ≥ 80"
- **Blocked categories** — e.g. "no agent may buy gift cards" (ties back
  directly to the prompt-injection gift-card example from StraitsX's own
  deck)

Keep this to 2-3 rule types max (see Section 13). The point isn't a
full policy engine, it's proving the merchant — not just us as developers —
owns the trust logic.

### Why this matters for the pitch
This section is what lets you say, truthfully, "we built the merchant
experience the track asked for," not just an agent-facing payment API with
a merchant label on it. It also gives you a second demo beat: after showing
the agent shopping end to end, flip to the dashboard and show the merchant
watching it happen and reacting to it live.

### 9.1 Connect directly, no repo needed
Claude Desktop (and Claude Code) can connect straight to a remote MCP
server over SSE, no intermediary tool required:

**Claude Desktop:** Settings -> Connectors -> "Add custom connector" ->
paste https://card.straitsx.ai/sandbox/sse (or /production/sse) -> Add.
Once connected, the card-issuing tools become available directly in your
Claude conversation, same as any other connector.

**For your own backend to call it (Python/Node, not via Claude chat):**
use an MCP client library to connect to the SSE endpoint directly and call
its tools programmatically. This is what your /authorise endpoint
ultimately needs to do: connect to the MCP server, call whatever tool
issues a card, get back the result.

### 9.2 Discovery script — the actual unblock

No dev docs exist for this MCP server, confirmed directly by StraitsX DevRel
(Daryl): *"Your agent should be able to understand how to interact with the
MCP server without the need for any developer documents."* MCP servers are
self-describing — connect properly and the tool list, parameters, and
descriptions come back automatically over the protocol itself.

Claude Desktop's "Add custom connector" UI hit an OAuth registration error
trying this (see Section 9.5 below), so instead, connect directly with a
small script using Anthropic's official MCP client library:

```python
"""
Direct MCP client — connects to StraitsX's card gateway and lists its tools.
Bypasses Claude Desktop's connector UI entirely.

Setup:  pip install mcp
Usage:  python discover_straitsx_mcp.py sandbox      # or: production
"""
import asyncio, sys, json
from mcp import ClientSession
from mcp.client.sse import sse_client

SANDBOX_URL = "https://card.straitsx.ai/sandbox/sse"
PRODUCTION_URL = "https://card.straitsx.ai/production/sse"

async def discover(url: str):
    print(f"Connecting to: {url}\n")
    async with sse_client(url) as (read, write):
        async with ClientSession(read, write) as session:
            init_result = await session.initialize()
            print("=== Server info ===")
            print(f"Name:    {init_result.serverInfo.name}")
            print(f"Version: {init_result.serverInfo.version}\n")

            tools_result = await session.list_tools()
            print(f"=== Available tools ({len(tools_result.tools)}) ===\n")
            for tool in tools_result.tools:
                print(f"--- {tool.name} ---")
                print(f"Description: {tool.description}")
                print("Input schema:")
                print(json.dumps(tool.inputSchema, indent=2))
                print()

def main():
    profile = sys.argv[1] if len(sys.argv) > 1 else "sandbox"
    url = SANDBOX_URL if profile == "sandbox" else PRODUCTION_URL
    try:
        asyncio.run(discover(url))
    except Exception as e:
        print(f"\n!!! Connection failed: {e}")

if __name__ == "__main__":
    main()
```

**Run it:** `pip install mcp`, then `python discover_straitsx_mcp.py sandbox`.
If it connects, the output IS the documentation, real tool names, real
parameter schemas, straight from the server. Wire `/authorise` (Section 7)
to call whatever tool this reveals. If it fails with an auth/OAuth error,
that's concrete evidence (not a UI quirk) worth taking directly to DevRel.

## 13. Research foundations

Our USP isn't invented from scratch — it's implementing the specific gap
that recent literature has identified as missing from current agentic
commerce protocols (ACP, AP2, UCP, MCP all handle *pieces*, none owns the
merchant's actual decision logic). Citing these in the pitch gives us a
"we're building what the research says is missing" narrative instead of
"we built an API."

### Core fit — cite these as our direct basis

**[2607.18347] A Decision-Centered Reference Architecture for Trustworthy
Agentic Commerce**
- **What it argues:** existing protocols each solve one slice (ACP =
  checkout exchange, AP2 = payment mandates, UCP = interoperable commerce
  capabilities, MCP = tool exposure) but none of them "should be mistaken
  for the merchant's complete internal decision model." The merchant still
  has to decide, on every request: is this action commercially valid, is
  the actor authorized, is checkout state current, is payment authority
  evaluable.
- **Where it maps in our PRD:** this is the architectural justification for
  our `/checkout` endpoint's decision logic (Section 6, step 5) — the
  moment where we check trust score against purchase risk before allowing
  a transaction to proceed. Frame our merchant decision layer as a
  concrete implementation of this paper's "missing internal layer."
- **Pitch line:** "We're not just building a checkout API — we're
  implementing the decision layer this paper identifies as absent from
  every current protocol."

**[2604.03976] Quantifying Trust: Financial Risk Management for
Trustworthy AI Agents**
- **What it argues:** introduces ARS (distinct from AP2) — where AP2
  governs *whether* a transaction is authorized to proceed, ARS governs
  *how financial consequences are handled once execution begins*. Trust
  isn't binary; it's a quantifiable input to risk decisions.
- **Where it maps in our PRD:** directly underpins Section 7's "Trust
  score inputs" subsection and the spend-cap-scales-with-trust logic in
  Section 3's goals. Use this paper's framing to justify *why* trust
  should be a continuous score rather than a pass/fail identity check.
- **Build implication:** consider structuring our trust score as a
  risk-adjustment multiplier on spend limits (à la ARS) rather than a
  simple threshold gate — gives us a cleaner story if judges ask "why a
  score and not just yes/no."

### Adjacent — supporting context, not the core citation

**[2505.19301] A Novel Zero-Trust Identity Framework for Agentic AI**
- **What it argues:** peer-to-peer trust establishment between autonomous
  agents from different trust domains isn't natively supported by
  existing standards (OAuth/SAML assume a hierarchical trust model, agent
  hands off with no equivalent).
- **Where it maps in our PRD:** feeds `/identify` (Section 7), specifically
  the "how do we even know it's the agent it claims to be" step *before*
  trust scoring can happen. This is upstream of our USP, not the USP
  itself — don't over-cite it as if it's about scoring.
- **Use case:** if a judge asks "how do you bootstrap identity without a
  shared authority," this is the paper to reference — but keep it in the
  identity-verification part of the pitch, not the trust-scoring part.

**[2511.15712] Secure Autonomous Agent Payments: Verifying Authenticity
and Intent in a Trustless Environment**
- **What it argues:** cryptographically non-repudiable proof of user
  intent (mandate or on-chain proof) is stronger authorization evidence
  than a traditional card transaction — merchants can point to a signed
  intent proof if a user later disputes a charge.
- **Where it maps in our PRD:** relevant to `/authorise` (Section 7) and
  the StraitsX one-time card validation step — reinforces why the mandate
  credential itself is evidence, not just a formality.
- **Note:** like 2505.19301, this is an identity/authorization-proof paper
  wearing trust-adjacent clothing. Use it to strengthen the authorise step,
  not as evidence for the scoring algorithm.

### Recommended pitch deck citation slide
Lead with 2607.18347 and 2604.03976 as "the two papers whose gap we're
filling." Mention 2505.19301 and 2511.15712 as "supporting the identity
layer beneath our trust engine" if asked a follow-up question.
